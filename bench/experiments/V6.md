## 3. Open defects, from code and traces

1. **A forced switch is priced but never compared.** `switchCheck` (`hooks/lib/policy.ts:232`) switches "whatever it
   costs" when `mandatory`. Two paths are mandatory:
   - the Haiku context trigger (`hooks/lib/triggers.ts`, `context` past `haikuMaxContext`)
   - the ladder's model `switch` (`runLadder`, `hooks/v4.ts`)

   On sqlglot (v5), the switches came at 159k tokens and then at 254k.
2. **Haiku's price step and its limit differ.** Haiku's price rises fivefold above 100k prompt tokens
   (`hooks/lib/prices.ts:21`), and `haikuMaxContext` is 150k (`hooks/lib/policy.ts:29`). postcss and sqlparse ran
   Haiku-only to about 140k (v5: $0.29 and $0.34, against Sonnet high's $0.17 and $0.13).
3. **No task budget.** Nothing bounds a task's spend. sqlglot cost $5.69 (v5).
4. **Reviews on prospective risk.** A judge's critical rating requires a review even when the diff shows nothing.
   That cost +$0.45 on 5 Sonnet tasks (v5).
5. **No contaminated state in the runner.** An edit to a behavior file during a run went unnoticed until a person
   saw it (v5).

## 4. What v6 changes (`strategy`, default `legacy`)

| Strategy | Start | Rescue | Review |
|---|---|---|---|
| `legacy` | as on main | the ladder: effort, fork, Opus consult, model switch | as on main |
| `v6a` | Haiku for T0, and for T1 with no risk; else Sonnet high | effort raise only; Opus switch only on observed critical evidence | observed risk only |
| `v6b` | as v6a, but Sonnet at the judged effort (medium allowed); high for complex, ambiguous or critical work | effort raise only, as v6a | observed risk only |
| `v6c` | as v6b | effort raise, then a fresh rescue builder one model up; never a mid-task switch past `rescueSwitchTokens` | observed risk only |

Every strategy also gets:
- the task budget (`taskBudgetUsd`), ending in `budget_exhausted`, never in done
- the Haiku context rule: at Haiku's 150k limit, the task gets a fresh Sonnet rescue under v6c, or holds under
  v6a/v6b. It never moves a large context. The 100k price step is no cue: a Haiku request at 140k still costs about
  a sixth of a Sonnet request at the same size, so staying is cheaper than any rescue (corrects defect 2's framing).

## 5. Experiments, budgets and stop rules

All runs use one frozen commit. The checkout is never edited while a run is live; fixes go in a separate worktree.
Each run passes `bench/preflight.mts`. Runs are never restarted after a code change.

| Run | Arms | Tasks | Paid sessions | Budget cap | Question |
|---|---|---|---|---|---|
| R1 `v6-strategies` | `v6a`, `v6b`, `v6c` (+ controls reused) | 30 | 90 | $40 | Which strategy, if any, beats Sonnet high? (E1, E3 and E4 in one frozen run) |
| R2 `v6-builder` | `v6c-builder` (`v6c` rows reused from R1) | 8 | 8 | $8 | Is builder delegation from the start ever worth it? (E2) |
| E5 multi-task sessions | | | | | Not run here; it needs its own plan and task set |

Stop rules:
- A run stops at its budget cap (runner admission).
- A run stops at once if its behavior files change (the `contaminated` check).
- After half the tasks, R1 continues even when an arm is losing, because stopping early would bias the comparison.
- A usage limit pauses the run, which resumes at the reset time.

Decision policies, one per arm, fixed now:
- `bench/experiments/policies/v6a-vs-sonnet.json`
- `bench/experiments/policies/v6b-vs-sonnet.json`
- `bench/experiments/policies/v6c-vs-sonnet.json`

## 6. Ship criteria (from the plan)

- No open false-completion defect.
- No verified-completion regression against Sonnet high.
- A net saving of 15% or more after all overhead.
- Task budgets tested.
- The same result on held-out tasks before any public claim.
- A single 30-task run is a release signal, not a general claim. Negative results get published.
