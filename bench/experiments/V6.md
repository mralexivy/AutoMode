## 3. Open defects, from code and traces

1. **A forced switch is priced but never compared.** `switchCheck` (`hooks/lib/policy.ts:232`) switches "whatever it
   costs" when `mandatory`. Two paths are mandatory:
   - the Haiku context trigger (`hooks/lib/triggers.ts`, `context` past `haikuMaxContext`)
   - the ladder's model `switch` (`runLadder`, `hooks/v4.ts`)

   On sqlglot (v5), the switches came at 159k tokens and then at 254k.
2. **Haiku's price step and its limit differ.** Haiku's price rises fivefold above 100k prompt tokens
   (`hooks/lib/prices.ts:21`), and `haikuMaxContext` is 150k (`hooks/lib/policy.ts:29`). The two need their own
   checks. At list prices, a Haiku request past 100k still costs about half of the same Sonnet request:
   - Haiku reads cache at 0.1× of its input price, Sonnet at 0.05×
   - so Haiku's cache read past the step is $0.05 per million tokens, against Sonnet's $0.10

   postcss and sqlparse ran Haiku-only to about 140k (v5: $0.29 and $0.34, against Sonnet high's $0.17 and $0.13).
   The cost there came from 45 requests, not from the price step.
3. **No task budget.** Nothing bounds a task's spend. sqlglot cost $5.69 (v5).
4. **Reviews on prospective risk.** A judge's critical rating requires a review even when the diff shows nothing.
   That cost +$0.45 on 5 Sonnet tasks (v5).
5. **No contaminated state in the runner.** An edit to a behavior file during a run went unnoticed until a person
   saw it (v5).
6. **The judges' cost was left out of the reports.** `cost_usd_api_equiv` is the CLI's total, and it does not include
   AutoMode's Haiku judge calls. That is about $0.02 per run. `rowUsd` (`bench/lib/decide.mts`) now adds them in every
   decision and report.
7. **False alarms, not false completions.** Across the 98 AutoMode rows of v2 to v5:
   - The gate never called a rejected task verified.
   - It called 9 tasks failed that the hidden tests accepted. Those false alarms bought the costly rescues.
   - The fixes in section 2 target them.
   - `bench/transcript-regressions.test.mts` pins the closest case (sqlglot v5): its stop is never read as verified.

Audit of the other paths the plan names:
- **Guardian (`hooks/guardian.ts`).** It reads each prompt before the router and changes no route. Nothing here
  touches it.
- **Workflow (`workflows/run.js`).** It runs only when the router picks `engineering-workflow`. The v6 builder is the
  agent `automode:builder`, called from a note to the main session. It never starts the discover, plan, build, verify
  and review pipeline.
- **Handoff (`hooks/lib/handoff.ts`).** It builds the rescue brief, capped at 21,000 characters. A rescue closes it
  with a builder's ask (`BUILD_ASK`), not the architect's.

## 5. Experiments, budgets and stop rules

All runs use one frozen commit, and they run in order, each with its own preflight. The checkout is never edited while
a run is live. Runs are never restarted after a code change.

| Run | Arms | Tasks | New paid sessions | Budget cap | Question |
|---|---|---|---|---|---|
| E1 `v6-e1-recovery` | `e1-v5`, `e1-rescue` (Sonnet high reused) | 10: the 6 v5 switch tasks + 4 that did not switch | 20 | $10 | With the same start, does fresh rescue cut the switch losses, and what does it add where no rescue is needed? |
| E2 `v6-e2-builder` | `v6c`, `e2-builder`, `e2-builder-rescue` | 8 matched tasks | 24 | $12 | Is delegation from the start ever worth it? |
| E3 `v6-e3-effort` | `v6b` (Sonnet high, Opus medium reused) | 30 | 30 | $12 | Does Sonnet at the judged effort, raised on evidence, beat fixed Sonnet high? Does the cache survive the effort change? |
| E4 `v6-e4-router` | `v6a`, `v6b`, `v6c` | 30 | about 52 (v6b from E3, 8 v6c from E2) | $22 | The full router |
| E5 `v6-e5-sessions` | `sonnet-high`, `v6c` | 5 sessions × 3 related tasks | 30 steps | $14 | Context growth, handoff loss, warm cache and cost over a continuing session |

The caps add up to $70.

Stop rules:
- A run stops at its budget cap. The runner admits no new session past it.
- A run stops at once if a behavior file changes. The row is `contaminated`.
- A usage limit pauses the run, which resumes at the reset time.
- A run is not stopped early because an arm is losing: that would bias the comparison.
- E5 reports only what its own rows show. No long-session claim comes from E1 to E4.

Decision policies, fixed now:
- E1: `e1-rescue-vs-v5`
- E2 and E4: `v6c-vs-sonnet`
- E3 and E4: `v6b-vs-sonnet`
- E4: `v6a-vs-sonnet`

| Rule | Value |
|---|---|
| Pass loss for ship | 0 tasks lost against the control |
| Pass loss for no ship | 2 |
| Cost ratio for ship | ≤ 0.85, with a 90% CI upper < 1.0 |
| No ship | CI lower > 1.0 |

## 6. Ship criteria (from the plan)

- No open false-completion defect.
- No verified-completion regression against Sonnet high.
- A net saving of 15% or more after all overhead, judges included.
- Task budgets tested.
- The same result on held-out tasks before any public claim. The confirm split in `heldout.json` holds 5 tasks.
- A single 30-task run is a release signal, not a general claim. Negative results get published.
